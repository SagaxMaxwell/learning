# 系统设计

参考 System Design School 的 [System Design Was HARD Until I Learned These 10 Patterns](https://www.youtube.com/watch?v=blMWTUVX43U)，按视频公开章节整理十类系统设计问题，每类下面再列具体技术。解释、例子和注意点为学习整理，不是逐字转录。

以图片分享应用为例：用户上传图片、浏览动态、点赞、搜索并接收通知。先明确瓶颈与一致性要求，再选择方案，不需要一次引入所有组件。

相关笔记：[[architecture|软件过程与架构]]、[[design-decisions|设计取舍]]、[[design-patterns|设计模式]]。

## 读扩展（Scaling Reads）

解决大量用户反复读取数据的问题。[视频 00:43](https://www.youtube.com/watch?v=blMWTUVX43U&t=43s)

### 旁路缓存（Cache-Aside）

应用自己管理缓存，减少重复查询数据库。

1. 先查缓存，命中就返回。
2. 未命中则查数据库，将结果写入缓存并设置过期时间，再返回。
3. 更新时，常见做法是先提交数据库，再删除对应缓存，后续读取重新加载。

- 例子：用户资料、图片详情读多写少，适合缓存。
- 取舍：删除失败或并发回填可能留下旧值；需要过期、失效重试或版本校验，不能直接当作强一致方案。
- 缓存异常时回源需限流，避免压垮数据库。穿透、击穿和雪崩见 [[learning/data/redis#Redis 异常|Redis 缓存问题]]。

### 只读副本（Read Replicas）

主库负责写入，并复制数据给副本；应用将适合的查询分配到只读副本。

- 例子：历史图片列表查副本；刚修改资料后的关键查询使用能满足一致性要求的读取路径，例如主库。
- 取舍：异步复制可能读到旧值。副本分担读压力，但不会直接扩大单主库写入能力，也不能替代独立备份。

### CDN

在靠近用户的边缘节点缓存资源，未命中时再回源。

- 例子：图片、缩略图、前端脚本由 CDN 分发，降低源站带宽与访问延迟。
- 取舍：使用带版本的资源 URL 或失效机制处理更新；私有图片必须正确鉴权并隔离缓存，不能因缓存泄露给其他用户。

### 数据预计算（Precompute）

提前生成昂贵查询的结果，读取时直接取汇总数据。

- 例子：定时或增量生成热门图片榜单，不在每次打开页面时重新扫描全部点赞记录。
- 取舍：额外占用存储和更新成本，需要处理迟到数据、重复事件与重算；结果可能有延迟。

预计算在查询前准备结果，旁路缓存通常在查询后复用结果；两者可以组合。

## 写扩展（Scaling Writes）

解决单节点存储或写入吞吐不足的问题。[视频 02:41](https://www.youtube.com/watch?v=blMWTUVX43U&t=161s)

### 分片键（Shard Key）

选择业务字段，通过范围、哈希或映射规则，把不同数据分配到不同分片；分片可以部署在不同数据库实例上。

- 例子：按 `user_id` 分片，同一用户的图片元数据放在同一分片，便于查询。
- 取舍：选键要兼顾均衡与常用查询；大用户仍可能形成热点，跨分片查询、事务和扩容迁移都会更复杂。

分片保存不同数据以分散负载，副本保存数据副本以支持冗余与读扩展，不是同一件事。

### 一致性哈希环（Consistent Hash Ring）

将节点与数据键映射到哈希环，常见规则是顺时针寻找第一个节点，由它负责该键。

- 例子：图片缓存增加节点时，主要迁移新节点接管区间的数据，减少重新分配范围。
- 取舍：虚拟节点改善分布，但不能解决单个热点键；数据迁移、复制和路由一致性仍需单独处理。

一致性哈希是路由策略，不是完整分片方案，也不是所有分片系统都用哈希环。

### 散射与聚集（Scatter-Gather）

协调者并行请求多个相关分片，再合并结果。

- 例子：统计全站图片数量，各分片返回本地计数，协调者求和。
- 取舍：查询会放大为多个请求；需要限制并发与超时，并明确部分分片失败时如何处理。跨分片排序、分页也要专门设计。

它主要解决分片后的跨分片查询，并不直接提升写入能力；能按分片键定位时，不必广播。

## 异步处理（Async Work）

将耗时工作移出请求等待路径，先受理，再执行。[视频 04:32](https://www.youtube.com/watch?v=blMWTUVX43U&t=272s)

### 队列与 Worker（Queue + Workers）

接口提交任务到可靠队列，返回任务 ID；后台 Worker 领取任务并处理。

- 例子：上传原图后返回已受理，Worker 后台生成缩略图。
- 取舍：队列能吸收短期高峰，但处理能力长期不足仍会积压，需要监控积压、等待时间和 Worker 负载。

“已受理”不等于完成；任务状态与入队的可靠衔接可结合后面的 Outbox 方案。

### 重试与死信队列（Retries + Dead-Letter Queue）

暂时性故障按退避间隔重试；超过次数或不适合继续处理的任务，进入死信队列等待排查。

- 例子：图片存储暂时不可用时退避重试；持续失败后告警，修复原因再受控重放。
- 取舍：区分可重试错误与永久错误，设置次数上限和随机抖动。重复执行需要幂等，不能假定消息只投递一次。

死信队列不是自动修复机制，需要监控、负责人和重放规则。

### 任务状态（Job Status）

独立保存任务的排队、执行中、成功、失败状态，以及结果或错误信息。

- 例子：客户端按任务 ID 查询缩略图是否生成；也可在完成后接收通知。
- 取舍：Worker 崩溃时不能永久显示执行中，需要超时检测与恢复机制；调用方超时也不能直接等同于任务失败。

## 扇出（Fan-Out）

解决一条内容如何进入大量关注者的动态列表。[视频 05:55](https://www.youtube.com/watch?v=blMWTUVX43U&t=355s)

### 写时扇出（Fan-Out on Write）

用户发布内容时，把内容 ID 写入各关注者的动态列表。

- 例子：普通用户发一张图片，后台批量更新其关注者的收件列表；用户打开动态时直接读取。
- 取舍：读取快，但写入放大，粉丝很多的账号可能制造大量任务；删除或权限变更也要处理。

### 读时扇出（Fan-Out on Read）

用户打开动态时，再获取关注账号的内容并合并排序。

- 例子：读取某用户关注的多个创作者近期内容，组成一页动态。
- 取舍：发布成本低，但读取时计算与请求增多；关注账号多时延迟更明显。

### 混合扇出（Hybrid）

普通账号采用写时扇出，超大粉丝账号的内容在读取时合并。

- 例子：普通朋友的动态预先写入列表，大 V 动态在打开页面时补入。
- 取舍：降低极端写入放大，但两条路径需统一排序、去重、分页和可见性规则。

## 热点键（Hot Keys）

解决总体容量足够，但单个键或分片承受过多请求的问题。[视频 07:16](https://www.youtube.com/watch?v=blMWTUVX43U&t=436s)

### 复制读（Copy Reads）

为热点数据提供多个可读取副本，把请求分散到不同节点。

- 例子：爆款图片的详情放在多个缓存节点，请求分流读取，而不是全部访问同一个键所在节点。
- 取舍：需要更新或失效所有相关副本；只增加节点却仍把热点请求路由到同一节点，没有解决问题。

### 拆分写（Split Writes）

把一个热点值的更新分散到多个子键，读取时再聚合。

- 例子：一张热门图片的点赞增量分散到多个计数分片，展示时汇总。
- 取舍：降低单键争用，但汇总与一致性更复杂；不能直接套用到要求精确原子扣减的库存或余额。

### 本地缓存（Local Cache）

在应用实例内存中缓存热点数据，减少访问远程缓存或数据库。

- 例子：短时间缓存热门图片信息，避免每个请求都访问 Redis。
- 取舍：每个实例各有副本，需要控制容量、有效期和失效传播；不适合未经设计就缓存必须实时一致的数据。

## 大规模计数（Counting at Scale）

解决高频点赞、浏览量或独立访客统计的写入与存储成本。[视频 08:31](https://www.youtube.com/watch?v=blMWTUVX43U&t=511s)

### 批量计数（Batching）

积累一批事件后，合并更新计数，减少逐次写入。

- 例子：同一图片的一批浏览事件合并成一个增量写入。
- 取舍：计数可见性会延迟；设置批大小和最长等待时间，处理重试去重与未刷盘数据，内存中暂存不代表可靠保存。

### 时间窗口（Time Windows）

按时间桶统计，再组合需要的窗口。

- 例子：每分钟记录浏览量，汇总最近一小时的桶，不扫描全部历史事件。
- 取舍：固定窗口与滑动窗口语义不同；明确事件时间、迟到数据和边界处理，桶粒度影响精度与成本。

### 近似计数（Approximate Counts）

在允许误差的场景使用概率数据结构，以更少空间统计大规模数据。

- 例子：用 HyperLogLog 估算独立访客数量，不保存每个访客的完整集合。
- 取舍：HyperLogLog 估算的是去重数量，不是普通事件总量，也不能返回成员列表；账务等精确场景不能随意使用。

## 大文件（Large Files）

避免让数据库和业务服务器直接承担全部大文件存储与传输。[视频 09:44](https://www.youtube.com/watch?v=blMWTUVX43U&t=584s)

### 文件与元数据分离（Blob + Metadata）

文件放对象存储，数据库只保存所有者、对象键、大小、状态等元数据。

- 例子：原图保存在对象存储，图片列表查询小型元数据记录，不读取整张图片。
- 取舍：上传中、处理中、可用等状态要清晰；处理孤立文件和悬空记录，不能假定两套存储自动保持一致。

### 预签名上传（Presigned URL）

业务服务鉴权后，签发限定对象、操作和有效期的上传 URL，让客户端直传对象存储。

- 例子：客户端申请上传许可，再直接上传原图，文件字节不经过业务服务器。
- 取舍：限制对象范围与有效期，按存储能力约束大小、类型；服务端验证上传结果，不能只凭客户端声明就标记可用。

### 分块上传（Chunked Upload）

把大文件分成多块独立上传，失败时只重传对应分块，最后合并。

- 例子：大视频上传到一半断网，恢复后继续上传缺失块。
- 取舍：记录上传会话和块编号，校验完整性，限制并发并清理未完成分块；小文件不必承担这套额外开销。

### 签名访问链接（Signed Links）

鉴权后生成短期有效的下载链接，用于访问私有文件。

- 例子：仅有权限的用户才能申请私有相册图片的下载链接。
- 取舍：链接通常是持有即可使用的临时凭证，泄露后到期前仍有风险；HTTPS、短有效期、日志脱敏和权限范围都要考虑。

CDN 缓存命中也不能绕过私有资源的访问校验。

## 实时推送（Real-Time Push）

让客户端及时收到变化，而不是不断刷新页面。[视频 11:02](https://www.youtube.com/watch?v=blMWTUVX43U&t=662s)

### 长轮询（Long Polling）

客户端发起请求，服务端等待有事件或超时再响应，客户端随后发起下一次请求。

- 例子：低频通知或任务完成提醒，通过普通 HTTP 获取变化。
- 取舍：兼容性较好，但仍有重复建请求的开销；需控制连接资源，并通过游标等机制补齐请求间隙的事件。

### 服务端事件（SSE）

通过持续的 HTTP 事件流，由服务端单向向客户端推送。

- 例子：缩略图处理进度、通知列表实时更新。
- 取舍：适合单向推送，客户端提交操作仍用普通请求；断线重连不等于自动补齐数据，需要事件 ID 和服务端补发能力。

### WebSocket

建立持续的双向通信通道，客户端和服务端均可发送消息。

- 例子：私聊、多人协作或高频交互。
- 取舍：需要心跳、断线恢复、连接鉴权和慢客户端处理；连接存活不代表业务消息已经可靠保存或消费。

### 发布订阅（Pub/Sub）

将事件路由到持有目标用户连接的网关，再通过 SSE 或 WebSocket 推送。

- 例子：用户连在网关 A，点赞事件发生在服务 B；通过订阅或连接路由，将通知交给 A。
- 取舍：需要连接归属、访问权限和离线补同步。发布订阅是否持久化取决于消息系统，不能把它自动等同于可靠消息存储。

发布订阅解决服务之间的事件分发，SSE、WebSocket 解决服务与客户端之间的传输，两者不是互相替代。

## 专用索引（Special Indexes）

根据查询方式选择索引，不把所有搜索都变成全表扫描。[视频 12:14](https://www.youtube.com/watch?v=blMWTUVX43U&t=734s)

### 倒排索引（Inverted Index）

建立“词 → 包含该词的文档 ID”映射。

- 例子：搜索“海边”，先找到包含该词的图片描述或标签，再排序返回。
- 取舍：需要分词、相关性排序与索引更新；数据库已更新不代表搜索索引立即更新，权限过滤也不能遗漏。

### Geohash

把位置编码为网格标识，利用网格筛选附近候选对象。

- 例子：查询附近拍摄的图片，先取当前位置及相邻网格的数据，再计算真实距离。
- 取舍：相邻地点可能跨网格边界，不能只查相同前缀；精度决定候选规模，Geohash 本身不是精确距离排序。

### 前缀树（Trie）

按字符前缀组织数据，快速定位共享前缀的词。

- 例子：输入用户名开头，显示自动补全候选。
- 取舍：树可能占用较多内存，需要处理更新、大小写和候选排序；前缀查询不等于任意子串或全文搜索。

## 故障处理（Handling Failure）

限制故障影响，并让重试、并发更新和跨服务流程保持可控。[视频 13:17](https://www.youtube.com/watch?v=blMWTUVX43U&t=797s)

### 超时与熔断（Timeout + Circuit Breaker）

超时限制一次调用的等待时间；熔断在下游持续异常时暂时拒绝调用，之后通过少量探测判断是否恢复。

- 例子：图片处理服务故障时，不让所有接口长期等待，可返回处理中或明确的暂不可用状态。
- 取舍：按整体延迟预算设置超时；超时不证明下游没有执行，重试仍需判断副作用。

### 限流（Rate Limiting）

按用户、接口或系统容量限制请求速率，保护共享资源。

- 例子：限制单用户上传频率，避免少数用户耗尽处理能力。
- 取舍：令牌桶可允许一定突发；分布式限流需协调配额。明确拒绝或等待策略，不能只把无限积压从接口搬进队列。

### 幂等键（Idempotency Key）

用唯一请求标识关联一次业务操作，重试相同操作时复用已有状态或结果，避免重复副作用。

- 例子：提交图片处理任务后响应丢失，客户端用同一键重试，不重复创建任务。
- 取舍：键需绑定调用方与请求内容；相同键不同内容应拒绝，并处理并发占用、处理中状态与保留期限。只在请求前查一次缓存不足以保证幂等。

幂等记录与业务变更需要一致提交或可靠协调，不能让两者之间的故障空隙导致重复执行。

### 乐观锁（Optimistic Locking）

更新时携带预期版本，只有当前版本仍匹配才写入，并增加版本号。

- 例子：两人同时修改图片说明，先提交者成功，后提交者发现版本冲突后重新读取或提示用户。
- 取舍：适合冲突较少的场景；版本比较与更新必须原子完成，不能用分开的查询和写入代替，也不能无条件覆盖重试。

### 事务发件箱（Outbox）

在同一个数据库事务中保存业务变更和待发事件，再由后台投递到消息系统。

- 例子：保存图片可用状态的同时记录发布事件，后台再通知动态服务，避免“数据库成功但事件没发出”。
- 取舍：发送成功但确认未保存时可能重复投递，消费者仍需幂等；监控待发积压并设计清理规则。

Outbox 解决数据库与消息发布之间的可靠衔接，不等于所有下游都在同一事务中执行。

### Saga

将跨服务流程拆成多个本地事务；某一步失败时，按业务规则执行补偿。

- 例子：购买付费相册涉及订单、扣款、授权；授权失败后关闭订单并退款，不能直接用一个本地数据库事务覆盖全部服务。
- 取舍：补偿是业务动作，不是数据库回滚。它也可能失败，需要重试或人工处理；已发送通知、已被查看的内容等副作用未必能撤销。

这些模式可以组合，但不会自动带来强一致或零故障。先确认需要保护的业务结果，再决定引入哪些机制。
