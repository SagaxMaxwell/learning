## 执行与存储

### 一条语句经过什么

1. 连接器建立连接并校验权限。
2. 解析器检查词法和语法。
3. 优化器选择执行计划。
4. 执行器调用存储引擎读取或修改数据。

MySQL 8.0 已移除查询缓存，不要把旧资料中的 Query Cache 当作现行能力。

### InnoDB 与 MyISAM

| 特性     | InnoDB         | MyISAM             |
|----------|----------------|--------------------|
| 事务     | 支持           | 不支持             |
| 行级锁   | 支持           | 不支持             |
| 外键     | 支持           | 不支持             |
| 崩溃恢复 | 更完整         | 较弱               |
| 常见用途 | 业务表默认选择 | 旧系统或特殊读场景 |

生产业务表通常优先使用 InnoDB。

### `EXPLAIN`

查看查询计划，重点关注：

- `type`：访问方式，通常希望避免 `ALL` 全表扫描。
- `key`：实际使用的索引。
- `rows`：优化器估算扫描行数。
- `Extra`：是否出现 `Using filesort`、`Using temporary` 等额外操作。

```sql
EXPLAIN
SELECT id, name
FROM employees
WHERE dept_id = 1
ORDER BY salary DESC;
```

## InnoDB 索引

### 聚簇索引与二级索引

- InnoDB 使用聚簇索引组织表数据，主键索引叶子节点保存整行数据。
- 一个表只能有一个聚簇索引，通常是主键。
- 没有主键时，InnoDB 会选择第一个合适的非空唯一索引；仍没有时会生成隐藏的 `row_id`。
- 二级索引叶子节点保存索引列和主键值，查询其他列时可能需要回表。
- 如果索引已经包含查询所需列，就形成覆盖索引，可以减少回表。

### 联合索引的 MySQL 语境

通用规则和示例见 [[sql#联合索引的常见理解]]。MySQL 的范围扫描、跳跃扫描和后续字段过滤依赖版本及执行计划，不把“最左前缀”当成无例外的口号。

### 索引下推

索引下推允许存储引擎先利用二级索引中的字段过滤，再减少回表次数。是否启用由版本和优化器决定，可以结合 `EXPLAIN` 判断。

## MySQL 事务特性

### 自动提交

MySQL 默认开启自动提交。需要把多条语句作为一个事务时，显式使用：

`START TRANSACTION` 或 `BEGIN`。开始、检查、提交与回滚的完整示例只维护在 [[sql#事务：让多步操作整体成功或失败]]，不要把 `COMMIT` 和 `ROLLBACK` 当成要先后执行的固定步骤。

### 当前读与快照读

- 快照读：普通 `SELECT` 通常读取一致性视图，不主动加锁。
- 当前读：读取最新版本并可能加锁，例如 `UPDATE`、`DELETE`、`SELECT … FOR UPDATE`。

### 日志的分工

- `redo log`：InnoDB 的物理日志，用于崩溃恢复和持久化。
- `undo log`：保存旧版本信息，用于回滚和 MVCC。
- `binlog`：Server 层的逻辑日志，用于复制和恢复。

## MySQL 锁

### 记录锁、间隙锁、临键锁

这些是 InnoDB 对索引记录和索引区间的加锁方式：

- 记录锁：锁住一条已存在的索引记录。
- 间隙锁：锁住索引记录之间的范围，阻止范围内插入。
- 临键锁：记录锁与间隙锁的组合，是 InnoDB 在可重复读下常见的范围锁形式。

锁的通用概念见 [[sql#常见锁]]；具体范围还受索引、隔离级别和查询条件影响，不能只按 SQL 文本猜测。

### 显式锁定

支持 `SELECT … FOR UPDATE` 的数据库都可用它表达事务内先读后改；通用示例见 [[sql#悲观锁与乐观并发控制]]。InnoDB 实际锁住哪些记录和间隙，仍取决于索引、条件和隔离级别。

### 乐观锁

版本号条件更新不是 MySQL 专有功能，见 [[sql#悲观锁与乐观并发控制]]。

## 复制与高并发

### 主从复制

MySQL 复制以 `binlog` 为基础：主库记录变更，从库拉取并回放。

常见用途：

- 读写分离。
- 故障转移和容灾。
- 数据备份或分析副本。

复制可能延迟，原因包括网络抖动、从库性能不足、从库读压力过大和主库大事务。读写分离后，刚写入的数据不一定能立即从从库读到，需要明确最终一致性边界。

### 分库分表

这是通用架构问题，不是 MySQL 专有功能，分片键、哈希与跨分片查询见 [[learning/engineering/system-design#写扩展（Scaling Writes）|系统设计]]。能通过索引、归档或合理拆表解决时，不要过早分库。
