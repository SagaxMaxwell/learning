# 数据持久化与 ORM

## 持久化与分层

持久化是把内存中的数据保存到数据库、文件或其他存储中。持久层集中处理读写，让业务逻辑不必直接依赖具体数据库或文件格式。

ORM 把对象与关系表映射起来，减少重复的行列转换和 CRUD 代码；它不是完整的业务层，也不会免除学习 SQL、事务与索引的需要。

## 如何选择

| 方式 | 适合场景 | 注意点 |
| --- | --- | --- |
| 数据库驱动 + SQL | 查询明确、报表复杂、需要细控 SQL | 参数绑定、连接管理和结果映射需要自己处理 |
| ORM | 常规业务 CRUD、关联模型和事务组织 | 留意 N+1、隐式查询、批量操作与迁移 |
| 混合使用 | 常规写入用 ORM，复杂查询用 SQL | 统一事务、连接与错误处理，不维护两套业务规则 |

ORM 的开销取决于查询、映射和加载方式，不应笼统认定“用了 ORM 就慢”。换数据库时，方言、类型、索引和事务差异仍需验证。

## 基本流程

1. 配置数据库连接与连接池。
2. 定义模型、主键、约束和映射。
3. 在明确的事务范围内执行读写。
4. 提交或回滚，并关闭会话、归还连接。
5. 通过迁移维护表结构，不依赖应用启动时随意改表。

## 主键选择

| 方案 | 特点 | 风险与取舍 |
| --- | --- | --- |
| 数据库生成的递增 ID | 简单，通常有较好的索引局部性 | 分布式合并、可猜测性与数据库语法差异 |
| UUID | 可独立生成，适合多个写入入口 | 随机 UUID 的索引局部性较差；存储格式和有序版本按数据库选择 |
| 雪花 ID | 时间戳、节点标识和序列号组成的整数 | 时钟回拨、节点号分配、整数精度和跨系统传输 |

SQLAlchemy 的主键可声明为 `mapped_column(Integer, primary_key=True)`，UUID 可用 `mapped_column(Uuid, primary_key=True, default=uuid4)`。这里的 `uuid4` 是函数对象，不是 `uuid4()`；避免所有记录共用定义模型时生成的同一个值。

## 连接与驱动

- `sqlite3` 是 Python 标准库驱动；SQLite 数据库本身独立于 Python。
- `pymysql` 是纯 Python MySQL 驱动；`mysqlclient` 依赖客户端系统库。不要仅凭实现语言判断实际查询性能。
- 不在多个线程中随意共享同一连接；按驱动约定使用连接池和事务。
- 不把密码写进笔记或源码。配置读取与业务逻辑分离，连接参数按部署环境注入。
- DBUtils 或 ORM 连接池解决连接复用，不代替事务管理。
