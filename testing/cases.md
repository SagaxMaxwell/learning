# 测试用例设计参考

按题目组织，每题先明确规则，再选用 [[methods|测试方法与用例设计]] 中适合的方法。表格列条件、操作和预期；并列检查项用无序列表。

- 有需求就能从黑盒入手；有源码才分析白盒覆盖，掌握部分内部设计再补灰盒。三者不是每题必填项。
- 等价类、边界值、判定表、状态迁移放在黑盒设计下；语句、分支、路径覆盖放在白盒设计下。
- 异常注入、组合、性能、回归按场景补充；集成、端到端说明验证范围，不是与黑盒互斥的分类。
- 选择依据是能否发现本题的具体风险，不是能否套上名称；需要源码、内部资料或负载目标的设计，先满足前提再使用。
- 条件不常见不等于无意义。能对应规则或风险就保留；仅特定前提下有效的注明前提；不确定的先确认，不直接删除。确认在本题范围内不可达且无相关异常风险，或已被同条件、同预期用例覆盖，才删去。
- 同一用例可覆盖多种方法，直接复用；不同故障位置或预期结果不能误删。
- 以下为练习约定，不代表微信、银行、ECU 或打印机的完整产品规则。操作真实依赖前准备隔离数据和恢复方式。

打印题先给可口述的参考回答，再展开用例。型号、功能和故障恢复规则以实际需求为准，不代表奔图的真实产品规格或面试原题。未提供驱动、固件源码，不编造白盒覆盖；拿到源码后再按 [[methods#白盒测试]] 补充分支与关键路径。

## 微信类消息的两分钟撤回

### 题目约定

本题讨论已发送到服务端的普通文本消息。先按以下约定设计，不视为微信的真实完整规则。

- 只有发送者本人可以撤回；消息不存在时返回不存在，不能影响其他消息。
- 以服务端记录的发送时间和撤回判定时间计算已发送消息的耗时；示例使用毫秒，实际按系统计时精度取值。
- 从发送成功到 `120000 ms`，包含截止时刻，允许撤回；超过上限拒绝。异常时间的处理规则另行确认。
- 成功后，消息状态变为已撤回；在线双方看到撤回提示，离线端重新同步后也应一致。
- 本人重复撤回返回“已撤回”，不重复变更或增加提示；已撤回后的重试不再受两分钟限制。

撤回不能让对方忘记已经读过的消息，也不承诺删除截图。真实项目要另确认消息类型、群聊、离线行为，以及恰好两分钟时是否允许。

本题未提供真实实现，不另编判定函数来凑白盒覆盖；白盒练习见后面的配置字题。

### 黑盒设计

#### 等价类

方法见 [[methods#等价类]]。除正在变化的条件外，其余都满足撤回要求。

| 类别 | 条件与操作 | 预期 |
| --- | --- | --- |
| 有效请求 | 本人撤回发送 60 秒的消息 | 撤回成功，双方最终显示撤回提示 |
| 无权限 | 他人撤回发送 60 秒的消息 | 拒绝，原消息不变 |
| 已超时 | 本人撤回发送 180 秒的消息 | 拒绝，原消息不变 |
| 目标不存在 | 使用不存在的消息 ID | 返回不存在，不误撤其他消息 |
| 已撤回 | 本人再次撤回同一条消息 | 返回已撤回，不产生重复提示 |
| 未登录或凭证失效 | 没有有效身份时请求撤回 | 认证失败，消息不变 |

“拒绝”不只看错误提示，还要检查消息状态没有改变。越权场景应直接调用接口，不能只验证界面没显示按钮。

#### 边界值

方法见 [[methods#边界值]]。固定为本人、存在且未撤回的消息，重点验证刚发送和两分钟截止处，不机械寻找一个负的下边界。

| 发送后的耗时 | 预期 | 检查点 |
| --- | --- | --- |
| 刚发送成功，如 `0 ms` 或 `1 ms` | 允许 | 确认消息刚建立就能撤回，无需为相同预期重复造用例 |
| `119999 ms` | 允许 | 刚好在上限内 |
| `120000 ms` | 允许 | 本题约定包含上限 |
| `120001 ms` | 拒绝 | 刚好超过上限 |

用可控时钟或测试数据制造边界，不靠手动掐秒。另测“客户端在 119 秒点击，服务端判定时已到 121 秒”，应拒绝；修改手机时间也不能绕过限制。

`-1 ms` 保留为条件性异常检查：若计时会受时钟回拨、跨节点时钟偏差或未来时间戳影响，用可控时钟或异常时间数据制造负耗时，按约定验证拒绝、校正或异常处理。没有这类风险时，不列为常规撤回用例，也不擅自规定“必须拒绝”。

#### 判定表

方法见 [[methods#判定表]]。本表前提是身份有效、计时正常；“—”表示该条件不影响本行结果，不代表 False。

| 消息存在 | 操作者是本人 | 已撤回 | 年龄在允许范围 | 预期 |
| --- | --- | --- | --- | --- |
| 否 | — | — | — | 返回不存在 |
| 是 | 否 | — | — | 拒绝，无状态变化 |
| 是 | 是 | 是 | — | 返回已撤回，无重复提示 |
| 是 | 是 | 否 | 否 | 拒绝，无状态变化 |
| 是 | 是 | 否 | 是 | 执行撤回 |

与等价类用例复用。另补一个有区分度的组合：消息已经撤回，再由他人请求，仍应拒绝，不能因为“已撤回”就跳过权限校验。

#### 状态迁移

方法见 [[methods#状态迁移]]。这里的“超时”是不可再撤回的业务状态，不要求数据库另存一个超时标记。

| 初始状态 | 操作或事件 | 预期状态与行为 |
| --- | --- | --- |
| 已发送、可撤回 | 本人撤回 | 已撤回，显示提示 |
| 已发送、可撤回 | 时间超过两分钟 | 仍可阅读，但不可再撤回 |
| 已发送、已超时 | 本人撤回 | 拒绝，内容不变 |
| 已撤回 | 本人在两分钟后重试 | 仍为已撤回，无重复提示 |
| 接收端离线 | 发送方撤回，接收端重连 | 同步为已撤回，不恢复旧正文 |

重点测完整序列，例如“发送 → 对方离线 → 撤回 → 对方重连”，不能只测单次按钮操作。

### 灰盒设计

适用前提是已知内部存在“状态持久化 → 异步通知”，并且通知允许重投。下面按此练习约定，检查状态已改但通知延迟、重复到达的风险；不代表微信真实架构。

| 利用的内部信息 | 操作 | 预期 |
| --- | --- | --- |
| 持久化与通知不是同时完成 | 撤回已提交、通知尚未送达时，查询状态并观察客户端 | 服务端为已撤回；客户端在约定同步期限内更新 |
| 通知可能重投 | 对同一消息投递两次撤回通知 | 最终只展示一次撤回效果，不恢复正文 |

接入真实数据库、通知模块时，同一用例也属于集成测试，不必另写一套。若没有内部资料，仍可按公开要求验证最终一致性，但不能声称覆盖了特定内部机制。

### 集成测试

保留这部分是因为“接口成功”不能证明状态已保存、通知已正确送达。按上述练习架构连接真实消息服务、测试数据库和通知模块；只让 Mock 返回成功不能验证这些协作。

| 设计依据 | 操作                  | 预期                        |
| ---- | ------------------- | ------------------------- |
| 判定表  | 本人调用真实撤回接口，核对数据库与通知 | 状态已撤回，通知对应同一消息 ID，接收方最终一致 |
| 判定表  | 他人绕过界面直接调用接口        | 服务端拒绝，数据库不变，无成功通知         |
| 状态迁移 | 同一发送者并发撤回同一消息       | 只有一次有效状态迁移，其余按已撤回处理       |
| 灰盒分析 | 复用前面的通知延迟、重复投递用例    | 实际持久化、通知与客户端去重行为符合约定      |

并发执行时保证消息仍在时间窗内。这里验证组件协作；若从真实客户端发送消息一直验证到另一端展示，范围会扩大为端到端。

### 端到端测试

撤回是用户可直接观察的跨端功能，核心链路需要少量真实客户端验证；时间边界和非法组合仍留在接口或单元层，不在端到端重复穷举。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 在线撤回 | 发送端发送消息，在时间窗内撤回，接收端保持在线 | 两端都显示撤回提示，旧正文不再作为当前消息展示 |
| 离线同步 | 接收端离线，发送端撤回，接收端重新连接 | 接收端同步为已撤回，不恢复旧正文 |
| 超时撤回 | 发送消息后超过时间窗，查看或尝试撤回入口 | 按交互约定隐藏、禁用入口或提示超时；消息不变 |

### 异常注入

方法见 [[methods#异常注入]]。断网重连用例也结合了状态迁移与时间边界；集中放在这里，不在其他章节重复。

断网用例中，本人在消息发送后 60 秒点击撤回，此时发送方突然断网；其余撤回条件均满足，接收方保持在线。90 秒和 130 秒均从消息发送成功起算，不是断网时长。用测试代理控制故障位置，避免只凭客户端报错猜测服务端状态。

| 注入位置与时机 | 制造方式与操作 | 预期 |
| --- | --- | --- |
| 原请求未到达，消息未撤回 | 阻断原请求并断网，90 秒时重连、重试，确保两分钟内完成服务端判定 | 撤回成功，双方最终显示撤回提示 |
| 原请求未到达，消息未撤回 | 阻断原请求并断网，130 秒时重连、重试 | 拒绝，原消息保留；不能因最初在 60 秒点击就允许补撤 |
| 已在窗口内撤回成功，响应未送达 | 丢弃成功响应并断网，90 秒时重连、同步或重试 | 显示已撤回；若重试，返回已撤回，无重复提示 |
| 已在窗口内撤回成功，响应未送达 | 丢弃成功响应并断网，130 秒时重连、同步或重试 | 仍显示已撤回；若重试，仍返回已撤回，不能误报超时或恢复正文 |
| 数据库更新时 | 使本次写入失败 | 不返回撤回成功，不发成功通知，原消息不变 |
| 状态已提交、通知尚未送达 | 阻断通知后恢复 | 按补发或重连同步机制达到一致，不恢复旧正文 |

- 自动补发还是手动重试按产品约定；恢复网络本身不代表请求已经重发。
- 是否允许首次撤回看服务端判定时刻，不看点击或重连时刻；即使 90 秒重连，拖到 121 秒才判定仍应拒绝。
- 若原请求已到达但仍在处理，需确认最终结果；客户端不能把断网直接等同于撤回失败，也不能在未确认时显示确定成功。

通知延迟用例与灰盒、集成设计复用；这里补充怎样制造故障。每次完成后恢复测试网络和存储。

### 组合测试

仅在本次范围同时包含多平台、在线与离线、单聊与群聊时使用；若只测服务端时间判定，不需要这张组合表。方法见 [[methods#组合测试]]，消息固定为本人在 60 秒内发送。

| 发送端 | 接收端状态 | 会话 |
| --- | --- | --- |
| Android | 在线 | 单聊 |
| Android | 离线后重连 | 群聊 |
| iOS | 在线 | 群聊 |
| iOS | 离线后重连 | 单聊 |

这四组覆盖三个二值因素的所有两两组合。每组都检查最终撤回状态；离线端应在重连同步后变更，群聊检查所有测试成员。

两两组合不等于覆盖所有三因素组合。如果某平台的“群聊＋离线”曾经出过问题，即使需要第五组也应补测。无权限、超时等规则由前面的用例覆盖，不与所有平台机械相乘。

### 性能测试

当本次验收涉及高峰容量或通知同步时限时，才开展下面的性能测试；只修改撤回时间规则，不必因此重做压测。方法见 [[methods#性能测试]]，峰值、规模、时长与指标先确认。

| 场景 | 负载设计 | 检查 |
| --- | --- | --- |
| 撤回接口高峰 | 逐步增加独立消息的撤回请求，并在目标负载下持续运行 | 吞吐量、P95/P99、错误率；权限和时间规则仍正确 |
| 通知积压恢复 | 暂停测试接收端后积压，再恢复消费 | 积压消退时间、同步延迟；不丢撤回状态、不恢复正文 |

使用新发送的消息，避免自然过期混入系统错误；临界时间请求另测。接口返回延迟和客户端最终同步延迟分开统计。

### 回归测试

假设修复了以下缺陷，复用本题用例验证原问题和相邻场景。

- 修复“两分钟整被拒绝”：重跑 `119999 / 120000 / 120001 ms`，不能把超时请求也放行。
- 修复“离线重连恢复正文”：重跑离线撤回序列，同时检查在线通知和其他端同步。
- 修复“重复撤回产生多个提示”：重跑并发请求、响应丢失后重试和重复通知。

## 配置字写入与回读

### 题目约定

正常流程为“解锁 → 写入 → 重启 → 重连 → 回读一致”。写入响应成功只是中间步骤，完整流程还要确认重启后配置保留、相关功能按新值工作。

输入沿用 [[methods#被测代码|ConfigService]] 的练习规则：恰好两字节且非全零。该代码只实现校验、写入和立即回读，供本题白盒练习使用，不代表真实设备的完整流程。

准备合法且可区分的旧值 A、新值 B、C，确认 A 已生效，列清受配置影响的部件与功能。权限、保存时序和生效时机以具体协议为准；实机测试前保存原配置，结束后恢复。

### 黑盒设计

#### 等价类

| 输入类别 | 代表输入 | 预期 |
| --- | --- | --- |
| 合法 | `b"\x01\x02"` | 完成解锁、写入、重启，回读与输入一致 |
| 部分字节为零 | `b"\x00\x01"`、`b"\x01\x00"` | 同样完成正常流程，避免把“全零禁止”错误实现为“任一字节为零就禁止” |
| 空输入或长度错误 | `b""`、一字节、三字节 | 报长度错误，不访问设备 |
| 两字节但全零 | `b"\x00\x00"` | 报业务错误，不访问设备 |

#### 边界值

- 长度取 `1、2、3`，另补空输入；两字节非零应进入写入，其余拒绝。
- 全零拒绝与非零允许复用等价类用例；这里没有数值大小规则，不额外套“数值最小值、最大值”。
- 复用等价类用例，不因“边界值”再复制相同输入。

#### 状态迁移

本表按“写入需解锁、重启后恢复未解锁”的协议设计；若回读也需权限，应按协议重新解锁后读取。

| 状态或场景 | 操作 | 预期与检查点 |
| --- | --- | --- |
| 正常流程 | 解锁、写入 B，重启完成后重连、回读并检查相关功能 | 回读为 B，所有受配置影响的部件与功能按 B 工作；重启前的解锁状态失效 |
| 未解锁写入 | 分别在首次未解锁、重启后未重新解锁时直接写入 | 均拒绝，配置不变，不能复用旧解锁状态 |
| 写入后不重启 | 解锁、写入 B，保持运行，不重启、不下电，检查各部件行为 | 要求重启后生效的部件仍使用 A；若允许立即生效，按约定时限检查 B。未完成正常流程，不能仅凭写入响应判为整项通过 |
| 连续写入，中间不重启 | 解锁后串行写入 B、C，分别确认写入成功；中间不重启、不下电，最后重启、重连、回读 | 最后成功写入的 C 被保留，重启后回读与实际功能均按 C，不恢复 A 或 B；文件和缓存检查复用灰盒设计 |
| 整机下电 17 小时后上电 | 解锁、写入 B，按规范满足保存时序后整机下电，确认断电并持续 17 小时，再上电、重连、回读；期间不重新写入 | 启动及初始化完成后回读为 B，所有相关部件与功能按 B 工作，不恢复 A 或默认值 |

- 连续写入用例需协议允许重启前再次写入；若不允许，改为验证第二次写入被拒绝，重启后仍为 B，不直接删除该检查。
- “全局生效”逐项检查所有受影响的部件与功能，无关功能保持不变。待加载配置是否能在重启前读到，按接口定义确认，不统一要求立即回读为新值。
- 整机下电须满足保存时序，并确认上电能否替代协议中的重启；休眠或断开通信不算整机下电。在授权台架按安全规程操作并记录时间。
- 17 小时按本题要求保留，用于长时间断电后的保持与加载检查；没有明确时间阈值，不机械补造“17 小时前后”的边界值。

### 白盒设计

这里只分析 [[methods#被测代码|ConfigService 示例代码]] 的输入校验、写入和立即回读，不包含解锁、重启或设备缓存。下面的覆盖结论只适用于该示例；实际流程还需结合真实源码检查，不能据此宣称完整流程已覆盖。

#### 语句覆盖

正常输入执行写入和回读；长度错误、全零和回读不一致分别执行三个 `raise`。每种情况都断言具体结果，不能只看代码跑到了。

#### 分支覆盖

| 路径 | 长度错误？ | 配置全零？ | 回读不一致？ | 预期 |
| --- | --- | --- | --- | --- |
| 长度错误 | True | 未执行 | 未执行 | `ValueError`，不访问设备 |
| 全零配置 | False | True | 未执行 | `ValueError`，不访问设备 |
| 回读不一致 | False | False | True | `RuntimeError`，已先写后读 |
| 回读一致 | False | False | False | 正常返回，已先写后读 |

这四条覆盖三个判断的真假出口。前面黑盒中已有的输入用例直接复用。

#### 路径覆盖

复用四条业务路径，再补两个依赖异常出口：

- 写入抛异常：原异常向上传递，不继续读取、不自动重试。
- 读取抛异常：原异常向上传递，不重复写入、不自动重试。

前置判断拒绝后不会到设备访问，因此不构造“长度错误但设备超时”的不可达路径。具体 pytest 写法见 [[methods#配置字服务的测试示例]]。

### 灰盒设计

已知设备存在缓存、持久化存储和启动加载环节时，利用内部检查点定位“未保存、未刷新、未加载”的区别。方法见 [[methods#灰盒测试]]；复用状态迁移中的操作，只补内部证据。

| 已知风险 | 操作 | 预期与证据 |
| --- | --- | --- |
| 只更新缓存、缓存未刷新或启动未加载 | 复用正常流程，保存完成后核对待加载缓存与可信存储检查点；重启后再核对运行配置、接口回读和实际功能 | 保存完成后待加载值与存储为 B；重启完成后运行配置、回读及功能对应 B。存储检查点须绕过缓存 |
| 连续写入后残留旧值 | 复用连续写入用例，检查实际存储文件或可信持久化检查点，以及待加载缓存（若存在） | 最终保存的为最后成功写入的 C，重启后回读和功能也按 C；不能只更新缓存，或被较早的写入覆盖 |

若规定重启后生效，重启前运行中的部件仍可使用 A，不能要求所有缓存立即变为新值。持久化失败的故障操作统一放在异常注入；仅按公开规则检查重启后结果，也可以是黑盒。

### 异常注入

按“解锁 → 写入 → 保存 → 重启 → 回读”的故障位置设计；保存可能由设备内部完成，不一定是独立命令。重启用例假定 A 已生效、B 已保存且需重启加载；在可恢复的授权台架或仿真环境中注入。

| 故障位置或时机 | 制造方式 | 预期与检查点 |
| --- | --- | --- |
| 解锁被拒绝 | 仿真器或测试设备明确拒绝解锁 | 报解锁失败，不继续写入、重启，原配置不变 |
| 写入被拒绝 | 设备明确拒绝写入；单元层可用 Stub 抛写入异常 | 不继续正常流程中的重启、回读；明确未写入时原配置不变 |
| 设备已写入、响应丢失 | 仿真器先保存，再丢弃响应 | 上层报超时，设备可能已变；先确认状态，不能盲目重写或继续正常流程 |
| 持久化失败 | 在待加载缓存更新后、保存完成前注入失败 | 不把完整流程判为成功；按协议检查错误上报及回滚或恢复状态，不擅自要求原子回滚 |
| 重启未执行 | 让重启请求被明确拒绝，确认部件仍在原运行状态 | 运行时继续使用 A，已保存的 B 不应因重启被拒绝而丢失；不能报告 B 已生效 |
| 重启已开始，启动未完成 | 在受控启动阶段注入失败或卡住 | 按约定超时报告启动异常；逐项确认配置加载情况，无法观测的部件标记生效状态未知，不能把不可用直接判成仍使用 A |
| 实际重启成功，但上层误判失败 | 丢弃完成通知或阻断状态查询，使上层超时 | 恢复通信后核实启动状态与实际功能；若 B 已加载生效，应确认实际结果，不能仅凭超时判定 B 未生效 |
| 重启完成，回读不一致 | 在模拟设备中制造回读旧值或默认值；单元层用 Stub 返回不同值 | 报校验失败，不把写入或重启成功当成整项通过 |
| 重启后回读断连 | 断开读取通道 | 报通信异常，不能确认回读一致；按恢复策略重连确认，不盲目重写 |

单元 Stub 只验证对应代码的异常处理，不能证明设备真实状态；实际流程还需检查操作记录，确认失败后没有误执行后续步骤。恢复操作按协议另行处理。

重启故障恢复后，不重新写配置，再完成一次正常启动，确认 B 仍保留且所有相关功能按 B 工作。未启动或无法读取，只能说明当前无法完成生效验证，不等于配置已丢失；确认失败发生在加载 B 之前，才能断言相应部件尚未应用 B。

### 集成测试

测试范围为“测试执行流程 → 真实 UDS 适配器与通信栈 → ECU”；验证全局生效时再连接相关部件。直接复用前面的用例，重点检查组件协作。

| 组件交界 | 复用用例 | 额外检查 |
| --- | --- | --- |
| 执行流程、UDS 适配器与 ECU | 正常流程、未解锁写入及异常注入 | 编码和响应解析正确，步骤先后符合协议；确认重启完成、重连后才回读，旧连接不误判为可用；失败阶段记录准确 |
| 配置存储、加载与相关部件 | 正常生效、连续写入及 17 小时下电 | 保存、启动加载和各部件使用的配置一致，实际功能符合新值，不能只验证一个回读接口 |

解锁、重启与恢复需要真实流程支持，`ConfigService.apply()` 没有这些能力。仿真器可以验证协议交互，但不能替代实机保存时序、断电保持与功能生效检查。

### 回归测试

- 修复“重启后配置丢失”：重跑完整正常流程，同时检查连续两次不同值的写入及长时间断电保持。
- 修改输入校验：重跑长度边界和全零拒绝，确认合法配置仍可写入。
- 修改通信重试策略：重跑“已写入但响应丢失”，防止重复执行有副作用的操作。

## 转账接口与资金一致性

### 题目约定

同一数据库、同币种、无手续费，余额和金额以整数分保存。转账金额必须大于零，账户有效且操作者有扣款权限；余额不足时拒绝。

扣款、入账和成功流水在同一事务中提交。幂等键绑定发起人及交易内容：相同键、相同内容返回原结果；相同键、不同内容拒绝冲突。

本题未提供源码，不凭需求编造白盒分支。以下内部事务假设用于集成检查；跨数据库转账需另按实际补偿与对账机制设计。

### 黑盒设计

#### 等价类

| 类别 | 操作 | 预期 |
| --- | --- | --- |
| 合法交易 | A 有 100 元，向 B 转 20 元 | A 减 20 元、B 加 20 元，成功流水对应本次交易 |
| 非法金额 | 分别提交零、负数、非整数分金额 | 拒绝，无扣款 |
| 余额不足 | 从余额 100 元转出 120 元 | 拒绝，双方余额不变 |
| 无效账户或无权限 | 分别用不存在的收款账户、他人的付款账户 | 拒绝，不影响其他账户 |

#### 边界值

付款账户余额固定为 10000 分，各用例独立恢复数据。

| 金额 | 预期 |
| --- | --- |
| `-1、0` 分 | 拒绝 |
| `1` 分 | 成功，覆盖最小合法金额 |
| `9999、10000` 分 | 成功；后一种余额恰好为 0 |
| `10001` 分 | 余额不足，拒绝 |

负金额可以直接通过接口提交，且错误处理可能反向改动余额，因此保留；不能因为正常界面不允许输入就删掉。

若有单笔或日累计限额，再围绕各自上下限补测，不自行增加限额数值。

#### 判定表

基础权限、账户和金额已合法；本表的“键已存在”指原交易已完成，聚焦重复提交。

| 幂等键已存在 | 交易内容相同 | 新交易余额足够 | 预期            |
| ------ | ------ | ------- | ------------- |
| 是      | 是      | —       | 返回原交易结果，不再次扣款 |
| 是      | 否      | —       | 拒绝内容冲突        |
| 否      | —      | 否       | 拒绝余额不足        |
| 否      | —      | 是       | 创建并执行新交易      |

已存在的请求仍需鉴权；已完成交易的重试不能因当前余额下降而重新判成余额不足。

原交易尚未完成时，同一键的重复请求按约定等待或返回处理中，不能提前报成功，也不能启动第二笔扣款。

#### 状态迁移

| 当前状态         | 操作或事件      | 预期             |
| ------------ | ---------- | -------------- |
| 尚未处理         | 合法请求完成事务提交 | 成功，余额和流水一致     |
| 执行中、尚未提交     | 发生数据库错误    | 不成功，事务回滚，无部分扣款 |
| 已成功、客户端未收到响应 | 用同一键重试或查询  | 返回原结果，不重复扣款    |

客户端“等待结果”不是交易失败状态；超时后先确认最终状态，不能直接再发一笔新交易。

### 灰盒设计

本题已知幂等键参与交易判定、扣款与入账在同一事务中提交，因此可以利用这些内部约束设计更有针对性的用例。没有这些内部资料时，仍可按接口结果和最终余额做黑盒验证，但不能验证具体事务边界。

| 已知内部信息 | 操作 | 预期 |
| --- | --- | --- |
| 幂等键保存交易内容 | 相同键先提交金额 A，再用相同键提交金额 B | 拒绝内容冲突，不创建第二笔交易 |
| 扣款、入账和流水共用事务 | 在入账前制造数据库异常 | 回滚后不保留部分扣款，不将事务内未提交的临时值当成最终结果 |
| 账户余额需要并发保护 | 两笔交易同时竞争同一付款账户 | 最终余额不为负，成功金额不超过原余额 |

这些用例还属于集成测试，因为需要真实服务和数据库；灰盒说明的是设计时利用了哪些内部信息。

### 集成测试

保留这部分是因为 Mock 无法证明真实事务原子性、幂等约束和并发扣款正确。连接转账服务与隔离的测试数据库，核对响应、余额和流水；前面的正常与金额边界用例按此范围复用。

| 设计依据 | 操作 | 预期 |
| --- | --- | --- |
| 等价类 | A 有 100 元、B 为 0 元，转账 20 元 | A 为 80 元、B 为 20 元，成功流水与交易一致 |
| 判定表 | 相同键分别提交相同内容、不同内容 | 前者返回原结果，后者拒绝冲突，均不重复扣款 |
| 状态迁移 | A 有 100 元，并发向 B、C 各转 80 元，使用不同键 | 无其他故障时仅一笔成功，A 剩 20 元，总金额不变 |

数据库故障与响应丢失继续使用下面的异常注入用例，不再复制一张相同的表。

### 异常注入

复用前面灰盒分析中的事务故障点，这里补充注入方式与验证结果，不另外复制测试实现。

| 注入时机 | 操作 | 预期 |
| --- | --- | --- |
| 扣款已执行、入账尚未执行 | 让后续数据库操作失败 | 同一事务回滚，双方余额及成功流水不变 |
| 事务已提交、响应尚未送达 | 丢弃响应，再用相同幂等键重试 | 返回原成功结果，只扣款一次 |
| 数据库请求等待时 | 在测试环境保持冲突锁，超过约定等待时间 | 有明确超时处理，无部分扣款，释放测试锁后可恢复 |

失败审计记录可按规则保留，不能把“没有成功流水”理解为“所有日志都删除”。

### 性能测试

存在吞吐量、响应时间目标或热点账户锁竞争风险时使用；单纯验证金额边界不需要压测。

- 多账户均匀转账：达到约定并发后观察吞吐量、P95/P99、错误率和数据库资源。
- 热点账户转账：集中操作少数账户，观察锁等待、超时和余额正确性。
- 两类负载分开统计，余额不足等业务拒绝不混入系统错误；使用测试资金和隔离环境。

### 回归测试

修复重复扣款后，复测相同键串行重试、并发重试、提交后丢响应；同时确认不同键的合法交易仍可分别执行。

## 电检任务与顺序依赖

### 题目约定

入口是提交电检任务，终点是设备结果、任务状态与报告一致。练习流程为“写特殊密钥 → 写 VIN → 传感器升级 → 写安全访问密钥 → 切换测试模式”。

- VIN 写入并回读通过后才能升级；依赖步骤失败则停止其后续步骤。
- 前置条件仍满足且可安全执行的独立检查继续，报告区分失败、阻塞和未执行。
- 同一设备串行执行任务；前一任务结束且设备状态确认安全后，才能开始下一任务。
- 这里没有提供调度器源码，不编造白盒路径。VIN 的具体格式规范另行确认，不擅自补充字符规则。

### 黑盒设计

#### 等价类

- 合法流程配置：可以受理；受理成功不等于最终测试通过。
- 未知操作、缺少必要参数：分别验证配置拒绝，并且尚未操作设备。
- 设备不可用：按约定拒绝或等待，不能假装执行完成。

#### 判定表

| 当前步骤结果 | 后续步骤依赖它 | 设备可安全操作 | 预期 |
| --- | --- | --- | --- |
| 成功 | — | 是 | 前置条件满足的后续步骤继续 |
| 失败 | 是 | 是 | 阻止依赖步骤，记录原因 |
| 失败 | 否 | 是 | 独立步骤可继续，原失败仍保留 |
| 任意 | 任意 | 否或未知 | 不继续危险操作，先恢复或确认状态 |

#### 状态迁移

- 提交 → 排队 → 执行 → 完成：设备结果、任务状态和报告对应。
- VIN 写入失败 → 依赖步骤阻塞：不能跳到升级成功状态。
- 设备断连 → 超时或恢复：不永久卡住，不将未执行标为通过。
- 前一任务结束但设备状态不明 → 新任务等待：不能仅因进程退出就释放给下一任务。

### 灰盒设计

按任务 API、Redis Stream、调度器和独立 pytest 进程组成的练习架构设计；已知同一设备需要任务级串行，因此检查参数传递、进程退出与结果汇总。

| 已知内部信息 | 操作 | 预期 |
| --- | --- | --- |
| API 先把任务放入队列 | 提交任务后在执行前检查任务标识和配置 | 队列中的任务与请求一致，不丢字段、不串车型 |
| 调度器一次处理一个设备任务 | 连续提交两个同设备任务 | 第二个任务等待，不与第一个同时启动设备操作 |
| 执行任务使用独立 pytest 进程 | 让进程异常退出 | 不误报成功，记录退出信息并保留已有日志；缺失报告明确标识，设备按规则恢复或等待 |
| 结果由执行过程汇总后保存 | 一条独立用例失败，其他用例完成 | 单项结果准确，整轮状态不被简单覆盖为全通过 |

利用内部架构找故障点属于灰盒视角；是否端到端取决于是否覆盖规定的完整链路，两者可以同时成立。

### 集成测试

保留这部分是因为单独验证 API、调度器或报告模块，发现不了跨组件的参数错配和结果丢失。

| 组件交界 | 条件与操作 | 预期 |
| --- | --- | --- |
| 任务 API → 队列 → 调度器 | 提交带车型和配置标识的任务 | 参数传递正确，不错配设备或配置 |
| 调度器 → pytest 进程 | 同一设备连续提交两个任务 | 一次只运行一个；设备未安全释放时第二个不开始 |
| 结果收集 → 报告存储 | 一项断言失败，其余独立用例完成 | 准确保存每项结果，整轮不能因进程正常退出就记为全通过 |

使用真实的被测交界组件；不在范围内的设备可以用仿真器隔离，并说明尚未证明实机行为。

### 端到端测试

本题的目标就是整轮任务交付，因此需要少量真实链路验证；不把全部输入边界重复跑到设备上。

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 正常整链路 | 从任务入口提交有效配置，执行到最终报告 | 步骤顺序正确，最终设备状态、任务状态和报告一致 |
| VIN 写入被拒绝 | 从入口执行，设备在 VIN 步骤明确拒绝 | VIN 项失败，升级等依赖步骤未执行且原因清楚 |
| 独立测试项失败 | 一项失败但设备仍安全、其他项前置条件满足 | 独立项继续，失败不被后续成功覆盖 |

`order` 只控制先后，不会自动处理依赖失败。不能只看 `skip` 标签，还应检查操作记录，确认被禁止的设备动作确实没有发生。

VIN 的全部输入边界优先在较小范围验证，这里保留关键成功与失败链路。

### 异常注入

| 故障时机 | 制造方式 | 预期 |
| --- | --- | --- |
| VIN 已写入、响应未返回 | 在可恢复台架丢弃响应 | 先确认状态；确认前不升级、不盲目重写 |
| 流程正在执行 | 在允许的安全阶段断开设备连接 | 按约定超时或恢复，不永久卡住、不误报成功 |
| 电检完成、报告正在保存 | 使测试结果存储暂时不可用 | 保留设备执行结果，标明保存失败；不为补报告重跑设备动作 |

这些故障可分别用于集成和端到端测试，区别是从哪个入口开始、验证到哪里。升级或写密钥等危险阶段不能无恢复方案地断电。

### 性能测试

当验收包含产线节拍、连续运行，或已观察到越跑越慢时，才做这部分。同一设备按安全流程串行多轮，记录阶段耗时、内存、连接数和失败率，不以非法并发换取提速。

同时检查任务结束后资源是否释放、后续任务是否持续变慢。只有使用相同测试范围与环境，耗时对比才有可比性。

### 回归测试

修改失败处理或调度后，至少重跑正常流程、依赖步骤失败、独立步骤失败和断连恢复；确认既不会错误继续，也不会把所有后续用例一律跳过。

## 文档打印与输出质量

### 题目约定

现场题是“给你一个打印功能，你怎么测试”。先确认支持的文件、操作系统、连接方式、纸张、单双面和验收指标；本题先测电脑应用经驱动打印到真实设备，不假设打印机能直接解析 PDF。

- 使用页码、文字、图片均可核对的 10 页 PDF，基线为 A4、单面、1 份。
- 已安装匹配驱动，设备就绪且纸张、耗材充足；用已知正常的文件与设备建立对照。
- 打印成功不仅是提交成功，还要核对实际输出和最终状态。质量按样张或约定容差判定。

### 现场参考回答

我会先确认支持的文件、连接方式、打印参数，以及成功的判断标准。先用标准文档跑通打印，核对内容、页数、顺序和状态，再用等价类、边界值补文件和参数场景，用状态迁移检查离线、缺纸后的行为。关键链路会接真实驱动和打印机验证，最后按要求测兼容性、性能与恢复，不能只看弹出“提交成功”。

### 黑盒设计

#### 等价类

| 类别 | 条件与操作 | 预期与检查点 |
| --- | --- | --- |
| 标准文档 | 打印基线 PDF | 输出 10 页、10 张，顺序与内容正确，无非预期空白页 |
| 不同内容 | 分别打印文字、表格、图片及图文混排文档 | 不乱码、漏字、重叠或截断；图片与表格符合版式和质量要求 |
| 特殊字符与名称 | 文件名含中文、空格、emoji；正文含产品支持的字符 | 文件能正确选取和提交；正文按字体支持情况渲染，不因名称异常崩溃。emoji 不天然属于非法输入 |
| 空白文档 | 打印一页真正空白的文档 | 按“跳过空白页”设置处理；不能把它等同于损坏文件 |
| 无有效文档 | 选择零字节、损坏或应用不支持的文件 | 在负责解析的应用或入口明确报错，不产生可执行打印作业、不误报完成 |
| 已知无权使用 | 在启用了打印权限控制的环境中，用无权账号提交 | 拒绝，不通过其他入口绕过；普通无鉴权设备不强加此规则 |

字体替代、彩色转灰度、留白和裁切先看规格；不把“不支持彩色打印”等型号限制报成缺陷。

#### 边界值

- 页数取 1、2 页和代表性多页，检查首尾页、分页和顺序；没有最大页数约束时，不凭空设一个上限。
- 若入口明确限制文件大小为 S，取 S 前后一个计量单位及 S 本身；构造的文件必须仍可解析，不能把损坏混成大小问题。
- 文字或图形放到声明的可打印区域边缘，验证缩放与裁切；非无边距机型不要求打印到纸张物理边缘。

份数、页码范围和单双面的边界由后面的专项题覆盖，不在这里重复展开。

### 端到端测试

从真实应用点击打印，经系统队列、驱动和连接到设备，直到实际出纸与作业结束。核对文件版本、目标设备、10 页内容、页序和状态；保存样张、任务标识、时间和版本，不能仅凭队列消失判成功。

关键异常复用后面的故障恢复题，不把每个文件边界都重复跑完整链路。

### 组合测试

仅在范围包含多个系统、驱动或连接方式时使用。按实际支持矩阵，组合“系统版本、驱动版本、USB/网络、文档类型”，可用两两组合缩减数量，再补高风险组合，例如特定系统下的网络双面打印。

不支持的组合不进入矩阵；两两组合不保证覆盖全部交互，历史缺陷必须定向保留。

### 性能测试

有速度、容量或稳定性目标时，再测首张输出、连续打印、并发提交与长时间运行。

- 区分冷启动、休眠唤醒和热机；分别记录提交、首张完成、整项完成的时间。
- 固定文档、连接、质量档、纸张和环境；单双面区分每分钟页数与纸张数。
- 连续多轮观察吞吐、失败率、内存和队列积压，结束后资源应释放；不能用单次结果判定性能。

### 回归测试

修复乱码或漏页后，复测原文档、其他支持字体、图文混排及多页首尾；驱动更新还要复测原有连接和常用打印设置。

## 双面、份数与逐份打印

### 题目约定

使用标有页码、方向箭头的 3 页文档；设备支持自动双面、长边/短边装订和逐份打印。每份独立成套，不把上一份末页和下一份首页拼到一张纸。

“份数”是完整文档的份数，不是单页的张数。设份数上限为能力或规格给出的 C，默认关闭跳过空白页、逆序和多合一等其他选项。

### 现场参考回答

我会把份数、单双面、装订边和逐份打印分开验证，再挑关键组合。比如 3 页打 2 份，单面是 6 张，双面应是 4 张，而且每份第三页的背面应留空，不能把两份拼在一起。还会核对长短边翻页方向，以及设置在预览、驱动和实际出纸之间是否一致。

### 黑盒设计

#### 等价类

| 设置 | 代表操作 | 预期 |
| --- | --- | --- |
| 单份与多份 | 分别打印 1 份、2 份 | 每份内容完整，不少份、多份或串页 |
| 逐份开启 | 单面打印 3 页、2 份 | 页序为 `1,2,3,1,2,3` |
| 逐份关闭 | 单面打印 3 页、2 份 | 页序为 `1,1,2,2,3,3` |
| 长边与短边 | 使用方向箭头文档分别双面打印 | 按所选装订边翻页时，正反面方向正确；横竖版分别选代表文档 |
| 不支持自动双面 | 对无此能力的目标设备请求自动双面 | 按规格禁用或拒绝，不显示已启用却静默单面；手动双面另按交互规则验证 |

逐份与双面组合能否选择、冲突时怎样处理，以能力定义为准；不凭经验认定所有驱动都支持。

#### 边界值

- 份数取 `0、1、2、C-1、C、C+1`，合并重合值；1 到 C 允许，其余拒绝，不悄悄截断。整数入口另测小数、空值和非数字输入，无法从界面输入时检查对应参数入口。
- 页数取 1、2、3：覆盖单页、完整双面和奇数末页。奇数最后一张背面按本题约定留空，不额外生成一张全空纸。
- 双面、2 份、逐份开启时复用 3 页文档，重点检查份与份之间的分页。

#### 判定表

固定 3 页、2 份、逐份开启；“—”表示后续设置不影响拒绝结果。页数指文档内容页，张数指物理纸张。

| 参数有效 | 支持自动双面 | 请求双面 | 预期 |
| --- | --- | --- | --- |
| 否 | — | — | 拒绝，不创建可执行作业 |
| 是 | 否 | 是 | 按本题能力规则拒绝或禁止选择 |
| 是 | 是 | 是 | 每份 2 张，共 4 张、6 个内容面，方向正确 |
| 是 | 任意 | 否 | 每份 3 张，共 6 张，逐份输出 |

### 集成测试

连接真实设置入口、驱动与设备，复用上表的关键组合，核对参数是否在组件之间正确传递。若界面、应用和驱动设置冲突，先明确优先级，再检查预览、实际任务属性和输出是否遵循同一规则。

纸面验证复用基线端到端环境，不因存在多个设置就为每一项新写一条完整链路。

### 回归测试

修复双面方向后，保留长边、短边、横版、竖版和奇数页；修复份数错误后，同时检查逐份开关、份间分页和单份打印。

## 页码范围与版式

### 题目约定

使用 10 页带页码、边界线的文档。入口支持单页、连续范围、逗号分隔，例如 `1-3,5`；本题约定重叠页去重并按原页序输出，默认单面、1 份。

支持横竖版、实际大小和适合可打印区域。页码语法、越界处理、逆序、多合一以及纸张尺寸不匹配时是否允许替代，都要先确认，不当成通用产品规则。

### 现场参考回答

我会用带页码和边界线的文档验证。页码选择按合法单页、范围、离散页和非法表达式分组，重点测第一页、最后一页及越界；版式则检查横竖版、缩放和纸张匹配。最终要核对实际打印了哪些页、顺序和内容有没有被意外裁切，而不只看预览。

### 黑盒设计

#### 等价类

| 类别 | 输入或操作 | 预期 |
| --- | --- | --- |
| 单页 | `5` | 只打印原文档第 5 页 |
| 连续范围 | `2-4` | 依次输出第 2、3、4 页 |
| 离散与重叠 | `1,3-5`；`1-3,3-5` | 分别输出 `1,3,4,5`；`1,2,3,4,5`，重叠页不重复 |
| 非法表达式 | `5-2`、`abc`、小数页码、范围模式下空输入 | 明确拒绝，不静默改成全部打印 |
| 实际大小 | 用已知尺寸的文档打印 | 不缩放；超出可打印区域的部分按已说明规则裁切，不承诺完整显示 |
| 适合区域 | 将大于可打印区域的页面缩放后打印 | 内容在目标区域内，比例和方向正确，不拉伸变形 |
| 不同方向 | 同一图样分别横版、竖版打印 | 内容布局与预览相符，不额外旋转或丢失边缘内容 |

#### 边界值

- 10 页文档取页码 `0、1、2、9、10、11`：1 到 10 合法，0 和 11 拒绝；不额外添加同类负数来机械扩充数量。
- 范围取 `1-1`、`10-10`、`1-10`、`1-11`：前三者分别为首、尾和全文，最后一项按本题规则拒绝，不能输出不明确的部分结果。
- 混合范围含非法页，如 `1,11`，整次拒绝，不只打印合法部分而隐瞒错误。

### 集成测试

当入口负责选页、驱动或设备负责排版时，复用离散页和缩放用例，核对原始页号、选页结果和最终纸张。尤其防止两层都执行选页或缩放，造成二次选页、重复缩小。

若只有单个纯页码解析函数，先做单元测试，不把解析函数的每个输入都称作集成测试。

## 打印队列与取消

### 题目约定

共享队列中的作业有唯一标识，可排队、暂停、继续和取消。本人可取消自己的作业，管理员可管理全部；其他用户无此权限。本题队列暂停不强制撤销设备已经接收的页面。

取消成功表示约定时间内不再处理该作业的剩余页面，不意味着已出纸的内容能收回；设备缓冲区中页面的停止范围和时间先按规格确认。

### 现场参考回答

这类功能重点是状态迁移和并发时序。我会分别在排队、发送中、打印中和完成后取消，核对状态与实际输出；同时测试重复取消、无权取消及取消 A 不影响 B。取消和完成同时发生时，要确认最终状态一致，不能既显示完成又显示已取消。

### 黑盒设计

#### 状态迁移

| 初始状态 | 操作或事件 | 预期与检查点 |
| --- | --- | --- |
| 排队中、尚未发送 | 取消 A | A 结束为已取消，不开始发送；其他作业不受影响 |
| 队列已暂停、A 尚未发送 | 提交 A，再继续队列 | 暂停时不发送 A，继续后 A 按调度规则执行，不丢失或重复 |
| A 已进入设备 | 暂停系统队列 | 尚未发送的后续作业停止发送；不能据此要求 A 立即停机 |
| 打印中 | 取消剩余页面 | 在约定停止范围和时限内终止，不回滚已出纸；最终不误记完整成功 |
| 已取消 | 再次取消 | 返回已取消或已结束，不重建作业、影响其他任务 |
| 已完成 | 尝试取消 | 返回已结束或不支持，不把已完成改成取消成功 |

不同层的暂停含义不同：系统队列暂停、设备暂停、单作业暂停不能混为一谈；有对应能力再分别验证。

#### 判定表

固定目标作业存在且处于可取消状态；授权以服务端或可信队列判断为准。

| 本人作业 | 管理员 | 预期 |
| --- | --- | --- |
| 是 | 否 | 允许取消自己的作业 |
| 否 | 是 | 允许管理员取消他人作业 |
| 否 | 否 | 拒绝，不改变目标作业 |
| 是 | 是 | 允许，结果与操作人身份记录正确 |

通过可用的管理接口验证授权，不只检查按钮是否隐藏。无效作业 ID 按接口约定返回，不误取消其他作业。

### 灰盒设计

已知“系统队列与设备内部队列分别维护状态”时，利用两个检查点选择竞争时机；不知道内部架构时，只做可观察状态测试，不宣称覆盖了内部缓存。

| 内部风险 | 操作 | 预期与证据 |
| --- | --- | --- |
| 客户端删除但设备未收到取消 | A 已在设备排队时，从客户端取消 | 核对取消是否传播、最终设备状态与输出，不能只看客户端条目消失 |
| 完成通知与取消同时处理 | 控制完成确认与取消的先后，分别执行两种顺序 | 最终只有一个符合规则的终态，不恢复已结束任务、不重复打印 |
| 任务标识错配 | 用不同用户、文件名提交 A、B，仅取消 A | 请求、队列和设备标识对应；B 内容与状态不变 |

### 集成测试

连接真实系统队列、打印后端与设备取消接口，复用前面的跨队列取消用例。若设备不支持按作业取消，应验证产品定义的替代流程，不能假定驱动一定能终止已接收任务。

### 回归测试

修复“取消 A 误删 B”后，重跑相同文件名、不同用户及连续提交；修复取消竞态后，重跑取消先到、完成先到和重复取消。

## 网络打印与故障恢复

### 题目约定

通过产品支持的网络协议提交作业；具体可能是 IPP 等，以实际设备为准。练习基线是“离线作业由系统队列保留，恢复后按规则续传”，是否需要人工确认、是否跨重启保存另行约定。

区分四个检查点：客户端已提交、队列已受理、设备已接收、实际打印完成。每个检查点的“成功”含义不同，不把通信成功当成纸张输出成功。

### 现场参考回答

我会先把离线发生的位置区分开：设备还没收到、设备已收到但响应丢失，以及打印到一半。三种情况不能都直接重发，否则可能重复出纸。再用状态迁移验证恢复，通过任务标识、队列、设备状态和样张核对结果；真实组件之间测协议和状态传递，少量关键流程跑到实际出纸。

### 黑盒设计

#### 状态迁移

| 状态或条件 | 操作 | 预期 |
| --- | --- | --- |
| 设备在线且就绪 | 提交已知文档 | 按基线打印，实际输出和最终状态一致 |
| 设备离线、尚未接收作业 | 提交，保持离线后再恢复 | 作业等待或按规格提示，不误报完成；恢复后按约定执行，不丢失 |
| 因缺纸而等待 | 提交后补充规格匹配的纸张 | 正确提示缺纸，补纸后按恢复规则继续，不跳页、错序或静默换纸 |
| 打印中卡纸 | 按授权流程清除卡纸并恢复 | 提示位置与恢复动作合理；按产品定义的重印范围核对页序和完整性 |
| 休眠 | 提交作业 | 约定时间内唤醒并处理，不因唤醒延迟误报完成或不断创建新作业 |

网络恢复、补纸或清除卡纸不一定都自动继续；真实产品不符合本题约定时，先修改预期，不把设计选择直接判为缺陷。

### 灰盒设计

如果已知客户端保存假脱机文件、设备返回作业标识，并提供可查询状态，就据此选择断点，关联客户端记录和设备记录。物理输出不可回滚，也不能仅因系统有任务 ID 就承诺“恰好打印一次”。

响应丢失时区分“未受理”和“已受理未确认”；若设备无法查询最终结果，应显示待确认或按明确的恢复策略处理，不伪造确定成功，也不盲目重发整个文档。

### 集成测试

| 组件交界 | 操作 | 预期 |
| --- | --- | --- |
| 系统队列 → 驱动或打印后端 → 网络接口 | 提交带特征页的文档 | 目标设备、作业标识和实际内容对应，协议受理不被直接映射为打印完成 |
| 设备状态 → 队列 → 客户端 | 分别制造缺纸、离线，再恢复 | 状态与错误正确传播，并在约定同步时间内收敛；无关作业不被错误覆盖 |
| 状态查询 → 完成确认 | 查询执行中与已结束的作业 | 区分执行中、失败、取消与完成；不存在的 ID 不映射为成功 |

这里用真实的被测交界组件验证协议与状态映射。协议仿真器可帮助制造时序，但不能替代真实设备出纸验证。

### 端到端测试

只选代表链路，从应用发起到实际纸张和最终状态：正常网络打印；提交前离线后恢复；打印中缺纸后补纸。响应丢失或设备重启的链路，在恢复规则和观察手段明确后再选取，不承诺穷举全部故障。

### 异常注入

只在授权隔离环境实施，记录任务、页码、注入时机和恢复方式；卡纸按厂商规程制造，不破坏设备。

| 故障位置与时机 | 注入方式 | 预期与检查点 |
| --- | --- | --- |
| 作业尚未到设备 | 在测试代理阻断传输，再恢复 | 不误报已打印，按离线保留策略恢复，最终内容完整 |
| 设备已受理、响应未到客户端 | 丢弃受理响应 | 查询或按规定确认原作业；不未经确认就新建重复作业，核对实际输出份数 |
| 作业传输一半 | 断开测试网络再恢复 | 不把部分接收当成完成；按协议续传、整项重传或失败规则处理，不出现无提示缺页 |
| 文档已部分出纸 | 在可恢复测试设备上受控重启 | 按规格确认已打印页、重印范围和剩余页；防止漏页或额外重复，不能臆定必须从下一页续印 |
| 假脱机文件写入时 | 在隔离目录模拟磁盘满或无写权限 | 不误报受理成功，不保留不可执行的正常状态；故障解除后新任务可用 |
| 打印后端处理作业时 | 停止测试进程后恢复 | 按持久化约定恢复或明确失败，不永久卡住；恢复前后核对任务与实际输出 |

传输中断与已出纸后的中断不是同一个故障点，不能因为都叫“断线”而合并。

### 现场追问

如果“提交成功却没出纸”，我会沿链路缩小范围，而不是直接重装驱动或重复点击：

1. 确认成功提示来自哪一层，记录时间、目标设备、文件和任务标识。
2. 看系统队列是否暂停、离线或等待；检查是否选错设备，是否有前序阻塞作业。
3. 看设备面板、连接和错误状态；按权限打印设备自检页，判断基础打印能力是否正常。
4. 用已知正常的小文档和客户端对照，区分文件、应用、驱动、网络与设备问题。
5. 有查询或日志时关联各层任务记录，检查受理、解析和执行分别停在哪一步；网络连通不等于打印协议正常。
6. 确认原任务是否仍可能执行，再按规程恢复并回归，避免补测时重复出纸。

自检页正常只能缩小硬件故障范围，不能证明驱动、网络协议和业务打印链路都正常。

## 多功能机的复印与扫描

### 题目约定

仅在设备和岗位范围包含这些能力时使用，不把它们当成所有打印机的必测项。先分清“纸张到纸张”的复印与“纸张到文件”的扫描；本题扫描到本机文件夹，不扩展邮件、云服务等未确认功能。

准备带页码、方向、文字和灰阶图的原稿。平板、自动进稿器（ADF）、双面扫描按支持能力选择，不支持的直接排除。

### 现场参考回答

复印我会核对份数、顺序、清晰度和缩放；扫描则核对内容、页数、方向、文件格式及是否真正保存。两者都有进纸和卡纸风险，但输出不同：复印看纸面，扫描看生成文件，不能因为预览正确就判定保存成功。

### 黑盒设计

#### 等价类

| 功能 | 条件与操作 | 预期 |
| --- | --- | --- |
| 复印 | 单页与多页原稿，按支持能力选平板或 ADF | 输出内容、份数和顺序正确；多页是否合为一套按交互规则验证 |
| 复印 | 选择原比例、支持的放大或缩小档 | 比例、方向和可打印区域符合预览与约定，不静默丢失内容 |
| 扫描 | 将多页原稿保存为支持的多页格式 | 文件可打开，页数、顺序和方向正确，正文可辨认，无丢页或多页 |
| 扫描 | 选择支持的颜色模式、分辨率和格式 | 文件属性与实际图像符合设置；黑白输出不以保留彩色为预期 |
| 扫描 | 目标路径含中文或空格；目标已有同名文件 | 合法路径可保存；按确认、改名或拒绝规则处理重名，不静默覆盖 |

扫描得到图片不等于具备 OCR；仅当明确支持识别时，再测可检索文本的准确性和语言范围。

#### 边界值

- 复印份数、缩放比例、扫描分辨率按各自声明范围取边界及相邻有效/无效值；离散档位不编造中间合法值。
- ADF 在装纸量上限 N 明确时取 `N-1、N、N+1`，超量只按厂商安全测试规程执行，不强塞原稿；不能安全制造时验证提示和装纸指导。

#### 状态迁移

- 多页扫描中取消：停止继续采集，已采集页按“保留部分文件或整项放弃”的约定处理，不标为完整成功。
- ADF 卡纸后恢复：按定义的重新放纸、续扫或重扫流程操作，最终页码连续，无未提示的漏页、重复页。

### 异常注入

对扫描目标目录分别制造无权限、空间不足，验证“采集完成但保存失败”有明确提示，不生成伪装成正常结果的损坏文件；恢复后新任务可成功。复印中的缺纸、卡纸恢复复用前面的进纸故障思路，但结果核对为复印输出，不再抄一套同样表格。
